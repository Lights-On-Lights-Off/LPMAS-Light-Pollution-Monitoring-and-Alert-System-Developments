## Monitoring data setup

The monitoring path is real hardware only:

`ESP32 + BH1750 -> Raspberry Pi Flask -> SQLite raw readings -> 1-minute Supabase aggregates -> dashboard`

No mock/demo sensor values are generated by the monitoring application.

### Raspberry Pi

1. Install the Pi dependencies from `pi-server/requirements.txt`.
2. Copy `pi-server/.env.example` to `pi-server/.env`.
3. Set `SUPABASE_URL` and the backend-only `SUPABASE_SECRET_KEY`.
4. Run `python3 pi-server/app.py`.
5. The application creates/migrates `pi-server/lpmas.db` automatically.

### Supabase

Run `supabase/migrations/0002_monitoring_data.sql` after the existing auth migration. It creates the minute aggregate table, cloud incident table and admin system-settings table.

### Greenhouse configuration

Managers configure each greenhouse from **Greenhouses** using:

- greenhouse name
- illumination start date
- illumination end date
- monitoring start time
- monitoring end time
- real sensors detected by the Pi API

No lux minimum/maximum/ceiling fields are configured by the manager.

### Fixed classification rules

During the configured illumination monitoring window:

- `>= 50 lux`: safe
- `31–49 lux`: warning
- `<= 30 lux`: violation

During the automatic 60-day dark phase after illumination:

- `0–15 lux`: safe
- `16–29 lux`: warning
- `>= 30 lux`: incident/violation

A confirmed incident requires 3 consecutive violation readings. With the ESP32's 10-second sampling interval, this is 30 seconds. One confirmed sustained breach creates one incident and sends at most one notification; the same incident is updated until a safe reading resolves it.

### Hardware Activity Log

Manager **Activity Logs** can select a configured greenhouse and export raw SQLite readings for Today, Last 24h or Last 7d. The export preserves the real sensor readings rather than replacing them with minute aggregates.
